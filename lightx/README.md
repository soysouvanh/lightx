# LightX Core Library

Welcome to the beating heart of the **LightX Framework**!

If you are a backend developer using LightX to build your application (for example, inside the `lightx-test` folder), you will rarely need to touch this folder.

This directory (`lightx/`) is the actual "Engine" under the hood. It contains all the complex Rust macros, code generators, and the embedded HTTP server (Hyper) that automatically compile your YAML/TOML files into blazing-fast native Rust code.

## What does this library actually do?

  <img src="../assets/generation.svg" alt="Macro Generation Pipeline" width="90%">

1. **The Code Generators (`core_generator.rs`, `handler_generator.rs`, `dao_generator.rs`)**
   During compilation, these files act as robotic assistants. They read your database schema and your TOML configuration files, and automatically write thousands of lines of bulletproof Rust code for you (like Database structures and HTTP endpoint logic).
2. **The HTTP Server (Hyper & Rustls)**
   LightX comes with its own ultra-fast, multi-threaded server. It natively handles HTTPS security (TLS) and automatically redirects non-secure HTTP traffic, so you never have to configure Nginx or Apache yourself!

3. **The `RequestContext` (The Data Bus)**
   When a user sends an HTTP request, LightX safely packages everything (the URL, the JSON body, the database connection) into a single object called `RequestContext`. You use this object in your business logic to do your work without ever worrying about memory crashes.

### Detailed Execution Flow (End-to-End)

Although the code generation is vast, the HTTP request lifecycle generated by LightX relies on highly strict, sequentially interlocking components:

1. **The Router (Core) & Validation:** The HTTP server receives the payload and the native Router (Core) resolves the path in `O(1)`. It then invokes the generated `check_parameters` to ensure the data integrity according to schemas and performs rigorous type casting.
2. **The Handler (AOP):** Fully generated, this acts as the orchestrator. It processes the _Business Objects (BO)* sequentially based on your TOML configurations: pure validations first, followed by transaction-safe processings.
3. **The BO (Business Object) - _Manual Code_:** The brain of your application! The manual code written by the developer takes over. It applies business logic algorithms to 100% reliable data and invokes the DAOs.
4. **The DAO - _Generated & Manual_:** If a DB interaction is required, the generated DAO lazily opens a connection and executes strictly typed SQL statements (or custom SQL macros you write).
5. **The Returns (HTTP Response):** As soon as the BO finishes, the AOP takes back control. If success is reported, the Core emits an SQL `COMMIT`. Otherwise, any error drops the context (RAII), triggering an immediate `ROLLBACK`.

### Generated vs Manual Layers

LightX enforces a strict division between human and machine responsibilities:

- **100% Generated Layers (Machine):** The HTTP Server, Router, `check_parameters` filters, `Handlers` (AOP), and the internal `DAO` machinery.
- **100% Manual Layers (Human):** Your descriptor `.toml` files (DB Dictionary & AOP Routings), and your native `BO` (Business Objects) Rust functions.

## The "Panic-Free" Promise

As you browse the source code in `src/`, you'll notice a strict architectural rule:
**We NEVER use `unwrap()` or `panic!()` in our routing or validation logic.**

If a user sends completely broken data, or a database connection stutters, the LightX engine is designed to elegantly catch the fault and convert it into a beautiful, standardized JSON error message for the Frontend. It will never crash the server.

## The "Zero-Test" Purity Architecture

LightX refuses to pollute your production binary. We architecturally enforce a strict separation of concerns:

- **Zero test code overhead**: All Mocking libraries (`SuperTest`), endpoint stubbings, and even intensive network Fuzz Testing modules are explicitly banished from the Core Engine. Your production artifact guarantees mathematical purity.
- **Dynamic Context Pools**: LightX's `RequestContext` is completely autonomously compiled. It extracts your database pool dependencies on-the-fly purely from your `.env` (yielding structures like `ctx.analytics_pool`). Unused database dialects are completely stripped out to conserve ultra-low memory footprints and ensure structural irreproachability.

### How to configure connections (The `.env` strategy)

LightX reads your `.env` file during macro compilation (`cargo build`). Any variable ending in `_URL` or `_DATABASE_URL` automatically spins up a production-ready asynchronous connection pool.

- **The Naming**: If you declare `USERS_DATABASE_URL=...`, LightX generates the exact field `ctx.users_pool`.
- **The Dialect**: The structural type is strictly inferred from the string prefix:
  - `sqlite:...` generates `sqlx::SqlitePool`
  - `mysql://...` generates `sqlx::MySqlPool`
  - `postgres://...` generates `sqlx::PgPool`
- **Backward Compatibility**: Using precisely `DATABASE_URL=mysql://...` acts as your default layer and safely yields `ctx.mysql_pool`.

## Installation (If building a new project)

If you are starting a completely new project from scratch, simply add LightX as a dependency in your `Cargo.toml`:

```toml
[dependencies]
lightx = "0.1.0"
```
